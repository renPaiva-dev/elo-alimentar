# Roteiro de teste — RF-03 (Listar produtos perto do vencimento)

Formato do AGENTS.md, Regra 3. Esta tela é só de leitura (RF-03, regra 6).

## Cenário de sucesso

- **Pré-condição:** API no ar (`npm run api`).
- **Passos:** `npm run checkpoint`. O roteiro cadastra "RF03 Produto A" (vence amanhã), "RF03 Produto B" (vence em 3 dias) e "RF03 Produto C" (vence em 5 dias), consulta `GET /api/v1/produtos?vence_em_ate=3` e depois apaga os três.
- **Resultado esperado:** HTTP 200; entre os três, aparecem só A ("vence amanhã") e B ("vence em 3 dias"), nessa ordem.
- **Automatizado:** `backend/test/validade.contrato.test.js` repete o BDD com as datas exatas da spec (hoje 01/10/2026; A 02/10, B 04/10, C 06/10) e o contador igual a 2.
- **Resultado obtido / data / responsável:** HTTP 200 com só A e B, nessa ordem, e os rótulos esperados (`npm run checkpoint`) · 06/10/2026 · Renato de Paiva Belarmino.

## Cenário de falha

- **Pré-condição:** existir produto com validade passada e quantidade maior que 0.
- **Limitação:** pela API não dá para criar esse produto, porque o cadastro e a edição bloqueiam validade passada (RF-01, regra 1). Na prática, ele aparece quando um produto cadastrado vence com o passar dos dias.
- **Passos:** `GET /api/v1/produtos?vencidos=true` e `GET /api/v1/produtos?vence_em_ate=3`.
- **Resultado esperado:** o produto aparece só em `vencidos=true`, com `dias_para_vencer` negativo e `rotulo_validade: null`, e não entra na lista principal nem no contador.
- **Automatizado:** `backend/test/validade.contrato.test.js` usa o produto D do BDD (validade 30/09/2026, 2 un).
- **Resultado obtido / data / responsável:** contra o banco real, `?vencidos=true` respondeu 200 (06/10/2026, Renato de Paiva Belarmino). O caso com o produto D vencido foi verificado só no Vitest, pela limitação acima.
